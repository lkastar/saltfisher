## 交付了什么

```
凭证导入 → 采集 → 筛选 → 命中判定 → 推送 → 收藏追踪 → 操作台
```

| 环节 | 要点 |
|---|---|
| 凭证导入 | 容器里没法过滑块，所以登录态 cookie 从面板粘贴导入，落盘后跨重启保留 |
| 采集 | mtop 签名直调为主，浏览器兜底；token 轮换自愈；**风控按端点隔离** |
| 筛选 | 九项条件。数据缺失时保守放行，并把「未验证」标注一路带到推送正文 |
| 命中判定 | 价格**进入**区间，而不是「见过没见过」——后者会永久漏掉降价进区间的商品 |
| 推送 | 邮件 / Telegram，一轮合并一条；发送成功后才写账本 |
| 收藏追踪 | 独立轮询，追降价与消失，与关键词规则解耦 |
| 操作台 | 六个页面。配规则、看采集有没有坏、管收藏夹 |

产品价值从**通知**出去。面板是操作台，按使用频率算一天开几分钟，不是盯着看的东西
——这个判断决定了它的形态：信息密度优先，视觉克制。

## 验收演练照出的九个缺陷

十六项演练在一个真实凭证、真实上游的环境里跑完。按严重度排，
**「为什么没被发现」是最值得看的一栏**。

### 1. 面板建的规则永远不通知任何人 · `71e1e64`

**从未可用**

- **症状**：规则采集正常、命中正常，但一条推送都发不出去。
- **根因**：`MonitorUpdate` 没有 `channel_ids`，建完就无法再改；而前端表单只发 `[]`
  且根本没有渠道选择器。
- **为什么没被发现**：收藏夹降价走的是「所有启用渠道」，那条路是通的。只有**规则命中**
  这条断了，而单元测试里的渠道是直接插库的，绕过了这个缺口。
- **影响**：这个产品的核心价值就是实时推送。跳过验收直接交付，等于交付一个不会通知的监控工具。

### 2. 容器从来起不来 · `7b7f27d`

**从未可用**

- **症状**：`docker compose up` 崩溃重启循环。
- **根因**：同一个版本号有两个独立来源——Dockerfile 手写的镜像 tag（1.56）和 `uv.lock`
  解析出的 playwright（1.62）。锁文件一更新就悄悄错开。
- **为什么没被发现**：本地装过浏览器，所以本地怎么跑都对。**唯一的交付路径从未被实跑过。**
- **修法**：不只是把 tag 改成 1.62（下次还会错开），而是 `uv run playwright install chromium`
  ——让浏览器从已安装的包里派生，两者不可能不一致。基础镜像只保留系统库价值。

### 3. `cp data/app.db` 会恢复出空库 · `e9c8577`

**数据丢失**

- **症状**：照文档做备份恢复演练，恢复后**每张表 0 行**。
- **根因**：WAL 模式下写入停在 `app.db-wal`，SQLite 只在 WAL 超过约 4MB 才自动 checkpoint，
  而进程关闭时既不 checkpoint 也不释放连接。

```
备份时:  114688 app.db
        3378432 app.db-wal   ← 3.3MB，所有数据在这里

三份 cp 出来的副本: 每张表 0 行，row_counts 返回 -1 哨兵值
                  → 连 monitor 表都不存在，CREATE TABLE 也还在 WAL 里
```

- **为什么没被发现**：这个项目**在任何时间点**照文档备份都会得到空库。连我在演练开头做的
  「基线备份」本身就是无效的——所以它不是我操作失误引入的，而是从第一天起就存在。
- **修法**：三处。`scripts/backup.py` 走 SQLite online backup API 并核对逐表行数；
  关闭时 checkpoint 并释放连接；四份文档改正。测试里有一条**专门断言裸文件拷贝确实会丢数据**
  ——那条哪天失败了，说明 SQLite 行为变了，这一节要重读。

### 4. DEBUG 日志泄露有效会话 token · `5dcf853`

**凭证泄露**

- **症状**：`SFD_LOG_LEVEL=DEBUG` 时 `httpcore` 打印完整响应头，含
  `Set-Cookie: _m_h5_tk=<live token>`。
- **根因**：代码压了 `httpx` 的日志级别，**没压底层的 `httpcore`**。
- **为什么没被发现**：第一遍审查是**按已知值** grep 的，全干净。泄露出去的是服务器刚**轮换**
  后的新 token——按原始值比对对它完全无感，而它才是当前有效的那个。改成按**模式**匹配才照出来。

### 5. 已删除商品的「消失」通知永不触发 · `8f10a77`

**静默失效**

- **根因**：真实 `ret` 是 `FAIL_BIZ_ITEM_DEL_NOT_FOUND`，而 `_GONE_MARKERS` 里三个名字全是
  没有真实数据时猜的，一个都匹配不上——注意它是 `ITEM_DEL_NOT_FOUND`，
  **不含 `ITEM_NOT_FOUND` 这个子串**。
- **影响**：贴已删除商品的链接得到 502 而不是 404；更要紧的是收藏夹检查把它
  **记成失败而非标记消失**，于是代码里那个 `gone` 通知对已删除商品永远不会触发。
- **验证**：用两个**真实已删除商品**端到端跑通：`reason='gone'`、状态 `on_sale → removed`、
  `last_error=None`（消失是观测不是失败）。

### 6. 会话不跨重启 · `71e1e64`

**白做工**

- **症状**：重启后面板要求重新导入 cookie，而用户早就导过了。
- **根因**：Playwright 把 cookie 恢复进了浏览器上下文，但 `UpstreamSession`（便宜路径用的）
  是纯内存的。
- **注**：token 轮换自愈的代码注释里专门警告过这一类事——「不要为服务器已经解决的问题去要求人
  手动重新导入」。同一个错误发生在了上面一层。

### 7. 卖家画像写到了没人引用的行上 · `8f10a77`

**静默失效**

- **根因**：搜索行的卖家 id 是不透明 base64，详情给的是数字，而 `upsert_item` 不改已有行的
  `seller_id`。
- **会咬人的场景**：贴链接加入收藏、且没有任何规则会搜到这个卖家 → 那个不透明行永远填不上画像
  → 收藏页**永久显示「卖家信用未知」，尽管我们明明抓到了**。
- **规模**：实测 199 行卖家里 2 个孤儿，299 个商品里 1 个指向数字 id。量不大，但后果是永久性的。

### 8. 会话状态的「绿色」是骗人的 · `7b73ccd`

**误导**

- **症状**：刚导入 cookie 后面板显示「会话可用」，而下一次真实调用立刻失败。
- **根因**：`adopt()` 导入时**无条件清空**风控标记，标记要等下一次调用失败才重新打上。
  所以「没有挑战」只代表**还没失败过**。
- **修法**：新增 `session.proven`——有过一次真实成功才为真。在那之前页面显示
  「凭证已导入，但还没有被验证过」。

### 9. 手动运行不记录采集路径 · `d3ae960`

**可见性**

- **症状**：「立即运行」成功后，规则列表的「路径」列仍是空的。
- **影响**：对**已停用**的规则，调度器根本不会跑它，所以这一列永久为空——而那恰恰是最需要
  知道走了哪条采集路径的场景。

## 两条方法论

不是风格偏好，是从上面那些缺陷里逼出来的，已写进 `.trellis/spec/`。

### 演示数据必须来自真实抓取，不能手编

理由不是好看。手编的演示数据在一次会话里产出了：Kindle 的标题配一张手机照片、
iPhone 12 标价 ¥410、四行商品共用同一张封面图。

**数据一旦不自洽，真 bug 就和坏 fixture 分不出来**——四张一样的封面让「图片错配」这类缺陷
完全隐形，而 ¥410 可能本身就是一个百倍换算错误。

换成从 `tests/fixtures` 真实抓取生成之后，**立刻照出三个**编造数据永远照不出的问题：
CDN 用 1×1 像素冒充 404（`onError` 永不触发）、真实商家标题 250 字炸开表格行高、
命中计数显示 0 却挂着 4 条记录。

### 密钥审查要按模式查，不能只按已知值查

第一遍拿 `.env` 里的十个真实凭证值去 grep 日志与全部端点，全部干净。

改成按**模式**匹配（`_m_h5_tk=[0-9a-f]{32}_\d+` 这类）之后，才发现传输层正在打印**轮换后**
的 session token。凭证会轮换，**轮换后的值同样敏感，而按值比对对它完全无感**。

前端 DOM 审查同理，并且要带**阳性对照**：这次在 localStorage 里「查到了」API token
（设计如此），它证明检测真的能查出东西——全阴性的结果如果没有阳性对照，可能只是脚本坏了。

## 我犯的两个错

记在这里是因为它们各自浪费了时间，而且都是可避免的类型。

1. **把假设当成事实说出去。** 我告诉用户去 cookie 里找 `x5sec`，说得像已知结论；实际它来自
   一份研究笔记「可行路径（待用户确认选哪条）」标题下的猜测。用户过了滑块却没有这个 cookie，
   白找一轮。名字碰巧是对的，**但取法是错的**——它只在过完挑战、且从那个具体请求的头里才拿得到。
   改成「从你要复现的那个请求上复制 Cookie 头」之后就通了，这条已写进文档。

2. **写了一行死代码，注释还声称它在起作用。** 我在 `adopt()` 里加了 `last_success_at = None`，
   注释说是它防止了继承旧凭证的健康状态。反向验证时删掉它，测试照样通过——真正起作用的是
   `proven` 里的时间比较。两套机制干一件事，而且我写错了归因。

另外有两次「先测再改」避免了写死代码：想给详情加浏览器兜底和 DOM 兜底时，先各测了一次。
第一次发现浏览器拦截的是同一个 API，兜底会是死代码；第二次发现被挑战的商品页渲染的是**推荐流**，
抓 DOM 会把别人商品的价格挂在请求的 id 下——对比价工具，自信地报错价比报错更糟。

## 已定与未决

### 快照保留策略（PRD 唯一未决项，已定案）

用 `dbstat` 量真实分表开销，而不是拿全库平均值：

| 表 | 字节/行（含索引） | 增长条件 |
|---|---|---|
| `item` | **1 813** | 每见到一个新商品 |
| `pricesnapshot` | **202** | 只在价格或状态**变化时**写 |
| `monitorhit` | 125 | 每条规则 × 商品一行 |

**结论：全量永久保留，不做降采样。** 一条规则连续跑 9.2 分钟（约 60 次观测）新增 **0 条**快照
——行量跟的是变价频率，不是轮询频率。外推（标注：是外推，不是跑满 24 小时的实测）：
10 条规则每天变价 2 次，一年约 **177 MB**。SQLite 毫无压力，而价格历史是这个产品最值钱的资产
——「这个价到底算不算便宜」只有历史能回答。

**方向更正**：无界增长的大头是 `item`（占一年增量 **71%**），不是快照。真要清理，第一个该动的是
已不被任何命中或收藏引用的 `item` 的描述与图片列表，不是价格历史。
**重新评估触发条件**：库超过 1 GB，或单商品价格序列超过 1000 点。

### 唯一未观测项：`itemStatus` 的「已售」真实取值

抓十条真实商品观测到：

| 取值 | 映射 | 次数 |
|---|---|---|
| `0` / 在线 | `on_sale` | 7 |
| `-2` / 已下架 | `removed` | 1（**保守猜测是对的**） |
| 走 `ret` 码 `FAIL_BIZ_ITEM_DEL_NOT_FOUND` | `ItemGoneError` | 2 |

**「已售」等不来**——观测窗口里没有商品刚好卖掉，这不受我们控制。默认分支落在 `removed`，
方向是安全的：错报消失会立刻被发现，错报在售则永远不会被跟进。而 PRD 本来就不声称能区分
卖出与下架（分析指标是「多久消失」，不是成交率）。**建议不为它单独立任务**，等自然发生即可。
