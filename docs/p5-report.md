## 一、`credit_score` 判定完了：上游给的是**等级**，没有**分数**

原本这是「卡在滑块上」的三件事之一。实际不需要——答案在已有的真实响应快照里。

- `tests/fixtures/detail_real.json` 的 `data.sellerDO.idleFishCreditTag.trackParams`
  **只有一个键**：`sellerLevel: "5"`。整个 payload 里与信用相关的键只有三个：
  `idleFishCreditTag`（容器）、`sellerLevel`、`zhimaAuth: true`（布尔，不是分数）。
- `SELLER_FIELD_MAP["credit_score"]` 找的是 `creditScore` / `score` / `sesameScore`，
  三个都不存在。
- 真库 253 个卖家，`credit_score` 非空 **0 个**；而真正抓过画像的 3 个卖家
  `credit_level` **全部有值**。也就是说画像抓取本身是好的。

按父任务的验收标准「不留永空字段」，**列与 UI 一起删了**。删除理由连同那份键名清单写进了
`spec/backend/collector-guidelines.md`——因为下一个人看到 `sellerLevel` 的第一反应就是
去加一个 `credit_score`，这正是那条记录要拦的动作。

已部署库里那一列留着无害（`add_missing_columns()` 只加不减，SQLModel 按名字选列），
没写迁移；这一点也有测试钉着而不是靠信任。

## 二、另外三条「解析出来了却扔掉」

- **`Seller.listing_count`**：`sellerDO.itemCount` 早就被解析进 `RawSeller` 了，
  只是表里没这一列，于是每次都被丢。建列。
- **`Seller.fetch_error`**：在这之前它**只会被清空、从没被写过**（真库 253 行全 NULL），
  于是「这个卖家画像为什么是空的」三天后没有任何答案。现在写异常类型 + 上游那句短话，
  在写入处截断 200 字符，绝不写 cookie / token / 响应体。
- **`/api/items?seller_id=`**：列早有索引，接口却没有这个参数。补上，
  query-count guard 按 3 行 vs 30 行**相等**断言。

## 三、一条差点静默一整周的 bug

失败的画像抓取也要盖 `fetched_at` 戳，否则每个周期都会重买一个刚失败的请求——这个理由是对的，
`a8baa25` 刚修掉的就是这类请求放大。

**但那个戳是拿 7 天*画像* TTL 去读的，不是拿某个失败退避窗口去读的。** 后果：一次风控挑战
会让当时筛过的每一个卖家**整整一周不再抓画像**，而且没有任何地方会说出来。

配套的清除路径加在重新导入凭证时（`resume_challenge_disabled`，和它重新启用规则是同一个
动作、同一个时机）。**只清风控这一类**——用 `pipeline.CHALLENGE_REASON_PREFIX` 判定，
所以那是个常量而不是两处手打的字面量；卖家自己的问题（商品已删之类）是真的黏性失败，
标记保留。

一般化的教训也记进 spec 了：**把一个「别再问了」的时间戳写进一个原本表示「数据有多新」的
列，就等于借用了那一列的过期语义**。要么配一条清除路径，要么单独开一列。

## 四、那两行数字 id：一行可删，一行必须留

父任务原本写的是「一对孤儿行」。实测**不是一对**：

| id | 昵称 | 有无不透明孪生行 | 被几个 item 引用 | 处置 |
|---|---|---|---|---|
| `195943285` | 中国村长 | 有（画像值完全相同） | 0 | 可删 |
| `2218219939144` | 小顾数码 | **没有** | **1** | **必须留** |

后者是一个 item 的活外键，删了破坏引用完整性，而且没有可合并的目标。SQL 与理由都写进了
`docs/operations.md`；253 行里 1 行，没写迁移脚本。

**顺带一条给 T1 的线索**：`2218219939144` 说明数字 id **能**出现在 `item.seller_id` 上，
id 空间不是纯不透明的。那行是哪条代码路径造成的没能确定（它唯一的快照是 `source='detail'`，
`first_seen_at` 比它唯一那条 `MonitorHit` 早四天），如实留成开放问题，没有硬猜。

## 过完滑块之后补上的部分

### T1：观测，不是猜

上一轮猜了三个 API 名字、三个全是 `FAIL_SYS_API_NOT_FOUNDED`——**每猜一次花一个真实
请求**。这次改成在浏览器里打开一个卖家主页，看闲鱼自己发什么。采集器**零请求**就拿到了
端点名、参数、响应形状。

结论落在父任务三分支的中间一条：**有端点，但只吃数字 id**（不透明 id 报
`FAIL_BIZ_BAD_REQUEST`）。映射路径：拿他任意一件商品打详情，读 `sellerDO.sellerId`，
每个卖家一次性一个请求。

### T2a：本项目第一个迁移脚本

`Monitor.keyword` 要变可空、要加互斥 CHECK——**SQLite 两件都做不到 `ALTER TABLE`**，
只能建新表拷数据换名。而 `monitor` 被 `MonitorHit`/`MonitorChannel`/`CollectRun` 三张表
外键指着。

实现方抓到一条我没想到的：**幂等判据不能只问「有没有 `seller_id`」**。那列是可空的，
`add_missing_columns()` 下次启动就会自己加上，而 `keyword` 仍是 NOT NULL、CHECK 仍然
没有——**「半迁移」是常态而不是边缘情况**。判据读三个事实。

真库迁移结果：3 行进 3 行出、每列逐行相等、500 条 `MonitorHit` 全部仍指得到 monitor、
0 外键违规、备份在 `data/backups/pre-001-*.db`。

### T2b + 一轮实测更正

`totalCount` 恒 0 而 `cardList` 非空——三次不同请求、两个卖家，稳定可复现。
判据只能是 `len(cardList)` 和 `nextPage`。

**两条我写进 brief 的「事实」其实是从字段名推的，实测都错了：**

- **`postInfo` 不是发布时间，是「包邮」标记**（邮 = postage）。这个端点根本不带发布
  时间。而且这个错**双向有害**：既在代码里写了句假话，又把真正的 `free_shipping_fact`
  数据扔了——包邮是规则本来就支持的筛选项。
- **`imageInfos` 是 JSON 字符串**，里面是完整图集。详情端点用同一个键名但那边是已解析
  的 list——**一个名字两种形状**。

还撞到一个长得像「顺手多要点信息」的开关：**`needGroupInfo: true` 会把选中的分组换成
默认组「综合」**（含已售出）。同样的 `groupName:"在售"`，`false` 拿到 3 件全在售，
`true` 拿到 20 件。现有实现传 `false` 是对的，记下来是防止有人为了拿分组名去打开它——
代价是把几十件旧货当新上架推给用户。

### T4b：入口设计与一句被删掉的假话

卖家规则从「命中商品」页建，不从规则表单建——表单里做选择器就要一个 `GET /api/sellers`，
而商品页已经有按卖家筛选，id 和昵称都在手边，**一个新接口都不用加**。

成功提示第一版写「去监控任务页给它加价格区间、排除词或推送渠道」。实现方指出
**`MonitorForm` 是只建不改的**，全 SPA 唯一的 `updateMonitor` 就是启用/停用按钮——
那句话会让用户去找一个不存在的控件。改成说实话：建好后改不了，要换条件就删掉重建。
