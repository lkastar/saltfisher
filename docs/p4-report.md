## 三条实测把设计推翻了

### 1. 推理模型会返回 HTTP 200 + 空回答，且不报错

| 调用 | max_tokens | completion | 其中 reasoning | 可见文本 |
|---|---|---|---|---|
| 视觉，问两个颜色 | 60 | 60 | **60** | **空** |
| 同一请求 | 1500 | 41 | 38 | `red blue` |
| 文本，「回复 ok」 | 1500 | 13 | 11 | `ok` |

`finish_reason: "stop"`、`prompt_tokens: 219`（证明图确实被处理），**content 是空字符串**。
连「回复 ok」都花了 11 个推理 token，所以不是长任务才有的问题。

设计 §9 把这种情况归进「结构化输出失败 → 提示检查提示词」。**那是指向错误原因**：
用户被叫去查提示词，而真正的修法是调大 token 预算。已给它独立话术，并加了第三种
`empty`（连 token 都没产生 → 指向模型 id 与端点配置）。

**判定条件也改了。** 初版按 `reasoning_tokens > 0` 判，但那只能抓到**会上报推理明细的
端点**；一个中转网关或本地 Ollama 返回同样的空 content 但推理计数为 0，就会掉回
`unparsable`——同一个误导换了一层。改成 `completion_tokens > 0`：**产生了 token 却没有
可见输出**才是信号，哪个计数器暴露它是端点自己的事。

### 2. 这个 CDN 从 `.jpg` 路径发 WEBP

实测 `...xy_item.jpg` → `200 / Content-Type: image/webp / RIFF…VP8X / 1920×864`，
且请求里**没有** `Accept: image/webp`。设计 §6 只写了 jpeg——按设计实现的下载器
**量不出尺寸、跳过每一张真实照片，把 100% 的商品降级成纯文本，还报告「格式无法识别」**。

另外两条同批实测：

- **1×1 阈值设计写错了**：设计说「任一维 ≤ 1」，而它让照抄的 `RemoteImage.tsx` 实际是
  `<= 2`。按前端来，两个界面对「缺失」的定义才不会打架。
- **`_400x400.jpg` 缩放后缀返回 `HTTP 420` + `rgv587_flag`** —— 图片 CDN 也有风控。
  所以图片下载**绝不能加重试循环**，而唯一能压小那 1.3MB 载荷的手法被拒绝了。

### 3. 一次点击可能计费两次

首答校验失败会自动重试一次。实测一次行情分析点击花了 **152 秒和两次计费调用**
（100s + 52s）。而响应里只有 `cached`——**`cached: false` 和「你刚付了双倍钱」在界面上
完全一样**。已加 `calls` 字段贯穿两个场景并显示出来。

## 按原始设计做的验收，照出四条

两个 fable 子代理按 `archive/2026-09/09-04-overall-design` 逐条验收，
明令禁止「因为文档这么说就判 MET」。结果：FR-7 的绝大多数条款 MET，四条不是。

### 已修：卖家画像每周期抓了就扔（**最严重，且是活的风险敞口**）

不在 P4 范围内但由 P4 的验收照出。`screen()` 每周期为每个通过本地筛选的商品抓一次画像，
`Candidate` 只带 `item` + `outcome`——**抓到的 `RawSeller` 被丢掉**，
`persist_cycle` 只写搜索行的身份信息。`settings.seller_profile_ttl_days`
**全项目只出现在定义处**，FR-3b 承诺的 7 天惰性刷新根本不存在。

实测填充率（2026-09-05，卖家行数每采集一轮就会变，看的是比例）：
**250 个卖家里 `fetched_at` 只有 6 个（2%），`credit_score` 是 0 个。**

代价是每个候选每个周期一次额外上游请求，然后扔掉——**正是把这个项目搞进风控的那种请求
放大，而修它的时候我们正卡在风控里**。已修：画像随 `Candidate` 带回入库；新鲜度集合在
`store` 里一次查询算好**传进去**（`collector/` 不许碰数据库）；存储用**商品指向的那个
id** 做键，避免复现 M1 那对孤儿行。

### 已修：删掉数据占位符的模板，会逼模型编数字并照常计费

原始设计第 246 行：「渲染时缺失占位符要报可读错误，**不静默塞空字符串**」。
实测把 `{stats}` 删掉，提示词从 1626 字变 352 字，但**保留了这两句**：

> 下面是关键词「iPhone 15」最近 30 天的**聚合统计数据**…只能依据这些统计量作答
> 每条 reason **必须指向上面给出的某个具体数字**

里面一个数字都没有。**这比"塞空字符串"更糟——它在逼模型编造，还照常计费约 150 秒。**

修法：分析路由在**花钱之前**用 409 拒绝，保存时不拒（用户可能改到一半，
丢掉半成品模板比存下它更糟），并把 `missing_placeholders` 放进场景配置的响应，
让警告出现在配置页而不是等 150 秒之后。

### 已修：入口该隐藏而不是禁用

原始设计第 259 行：「默认关闭；场景未配置或未启用时对应入口**整体隐藏**，不得报错」。
实现给的是禁用 + 提示，且**后续阶段文档把「隐藏」这句悄悄弄丢了**。

按契约改成隐藏。理由站得住：这个功能**默认关闭**，所以一个永远点不动的按钮
正是大多数用户会一直看到的东西；发现入口属于设置页，就在那个开关旁边。

### 未修，记录在案：设计的「无需二次迁移」这条不成立

`design.md` §8 的验收清单里有一条「数据模型能同时支撑 FR-6 与 FR-7，**无需二次迁移补历史
字段**」。事实是 M2 加了 `CollectRun`、P3 加了 `CollectRun.pages` 与
`MonitorHit.last_hit_at`，**后两者都是不可回填的历史字段**。

代码对此是诚实的（`legacy_clock_rows`、`collected: false` 把补不回来的过去标出来），
但设计当时的那句断言是错的，这里记下来，免得下一个读者把它当事实。

## 安全约束是结构性的，不是约定性的

`MtopClient` 的 httpx client 带着闲鱼的 cookie jar。复用它等于**把用户的登录态发给第三方
LLM 端点**。

所以 httpx client 由调用方注入（`app.state.notify_client`），`app/llm/` **不 import
`app/collector/` 的任何东西**，并且有一条测试 grep 每个文件确认这一点——
让它在结构上不可能发生，而不是靠自觉不去做。

密钥同理：**没有任何响应模型带 `api_key` 字段**，所以不存在「忘了脱敏」的返回语句。
测试用**模式**扫全部 8 条路由 + `/openapi.json`（M1 的教训：按模式查而不是按已知值查），
并反向验证过——把字段加回去，测试立刻红。

## 反向验证

| 撤掉的东西 | 变红 |
|---|---|
| `starved` 判定改回 `reasoning_tokens > 0` | `a gateway that hides the breakdown gets misdiagnosed` |
| `starved` 恒 False | 3 条，含「用户拿到『检查提示词』」那条 |
| `_scrub` 直接返回原文 | 密钥泄漏那条 |
| 列表端点改成逐行 `select` | 4 条查询（3 行）vs 31 条（30 行） |
| 数据占位符的拒绝 | `billed for a prompt that could only be answered by inventing` |
| 画像不带回 `Candidate` | `the profile was fetched and discarded` |
| 去掉 TTL 门 | `re-bought a profile it already had` |

**一个查询数守卫的盲点**（评审反向验证时发现）：`session.get` 逐行取发 **0 条 SQL**
（身份映射直接给），而 `select()` 逐行取发 5 条。所以 `before_cursor_execute` 等式守卫
**对 `session.get` 形状的 N+1 完全不可见**。已写进 `database-guidelines.md`。

## 已定与未决

### 已定

- **两条独立路径**，不是一个函数带 `scenario` 分支：输入、成本、缓存都不同。
- **`market` 缓存、`item` 不缓存**。缓存键是渲染后提示词全文 + 端点 + 模型的 sha256，
  不设 TTL（键随统计量移动，过期时钟只可能两个方向都错），只缓存 `ok`
  （缓存一个 `starved` 会在用户调大预算后仍然挡住重试）。
- **`sample_size == 0` 根本不调模型**（`no_data`，零计费）。一个被问「零件商品的价格水位」
  的模型，答得和有数据时一样流畅。
- **五种结果状态**（原 PRD 写三种是错的）：`ok` / `starved` / `empty` / `unparsable` /
  `no_data`，每种有各自的修法，话术全部由服务端给出、前端不自己写。
- **`max_tokens` 是场景配置项**，不只是 Python 默认值——**报错指向一个产品没有提供的旋钮，
  和报错指错原因是同一种失败**。
- **`market` 的 `send_images` 强制为 False**：那条路径从不发图，存 `true` 是记一个谎。

### 未决

- **`credit_score` 是上游没有还是解析丢了**：`base.py:165` 有 `creditScore/score/sesameScore`
  三个别名，0/250 命中。两份验收都判「无法验证」——需要一份真实详情响应才能定，
  而那要等风控解锁。
- **图片代理**：设计承诺过 `GET /api/images/proxy` 作为防盗链兜底，没实现。
  M1 实测过这个 CDN 不看 referer，所以现在不需要；但这是一次**未记录的需求收窄**，
  已在此记下。
- **`SettingsPage.tsx` 1013 行**，早过了 spec 的 ~400 行拆分触发点，而
  `AnalyticsPage`(620) 与 `MonitorsPage`(518) 也一样。要么触发点是错的，要么代码库是错的，
  该定一个。
