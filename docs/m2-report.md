## 设计里的四项指标，为什么只做三项

设计 §8 列了四项。**「消失时长」推迟**，理由是它的偏差是结构性的，不会随时间变好。

| 指标 | M2 | 依据 |
|---|---|---|
| 价格分布 | ✅ | `iPhone 15` 关键词下 264 件，样本已足 |
| 降价排行 | ✅ | 样本随时间自动变厚，代码不需再改；唯一直接回答「该买哪个」的指标 |
| 供应量趋势 | ✅ | 依赖新增的运行日志 |
| 消失时长 | ❌ | 见下 |

设计的算法是「对 `status != on_sale` 的商品做 `last_seen_at - first_seen_at` 分布」。
两个前提都不成立：

1. **`status` 在关键词范围内没有信息量。** `app/store.py` 里唯一把 `status` 改成
   `removed` 的地方只在**收藏项详情抓取报告商品不存在**时触发。关键词规则的商品掉出
   搜索结果时无人改它。实测：库里 **327 件商品，`status != 'on_sale'` 的是 0 件**
   ——该指标恒空。收尾时重测过，仍然是 0。

2. **退回 `last_seen_at` 也不行。** `app/scheduler.py` 写死 `rows=30`，每周期只看
   搜索结果前 30 条。「掉出前 30 名」与「已下架」永远无法区分，而这个偏差从第一天到
   第一百天完全一样。

所以它不是"数据还不够"，是"观测口径不支持"。**已排入 P3：先做搜索翻页把口径扩开，
再补这项指标。**

## 三条被真实数据改掉的设计

### 1. 采集失败的周期原本无处可查

设计对供应量趋势明确要求「采集失败的周期必须可识别，否则会画成『那天没货』」，
但没给承载它的表。`Monitor.last_error` 只有当前态，`NotifyLog` 只记通知。

**实测复现了这个陷阱**：按 `Item.first_seen_at` 分组，库里只有 `08-31`（4 件）
和 `09-04`（312 件）两天有数据，`09-01`~`09-03` 是 0——那三天是**没在跑**，
不是那三天没货。仅凭库里的数据无法区分。

这与 `PriceSnapshot` 同性质：**当时没记，以后补不回来**。所以 `CollectRun`
排在 M2 第一位，先让日志开始积累。

### 2. 日期不能按 `Item.first_seen_at` 归

设计说供应量趋势「按 `first_seen_at` 日期分组」。但那是全局字段，两个关键词共享的
商品会归错日期。

**真实库里这两个字段差 4 天**：`Item.first_seen_at` 最早 `2026-08-31`，
而 `MonitorHit.first_hit_at` 最早 `2026-09-04 09:40`——那 4 件 08-31 的商品是
demo 种子数据，早于现在这三条规则。按设计原文实现，会对一条台账只有 8 小时的关键词
声称「已收集 5 天」。

改用 `MonitorHit.first_hit_at`（每规则×商品）。

### 3. 不引 pandas

设计说「全部在 `analytics.py`，pandas 读 `PriceSnapshot`」，而 `pyproject.toml` 里
**没有 pandas**——spec 的 stack 表也一直这么写，属既存失真。

三个指标是 3 个 `GROUP BY` 加一次 `statistics.quantiles`，样本在百级。为此引
pandas + numpy 给运行镜像加数十 MB，换不到对等价值。**升级触发点已写进 spec**：
出现需要 join/reshape 的多维指标，或样本进入十万级。

## 关键词不是商品品类 —— 这个口径必须让用户看见

`Item` 上没有 keyword，范围只能经 `MonitorHit` → `Monitor.keyword` 反查。
实测重叠：

| 关键词 | 商品数 | 与 `iPhone 15` 的交集 |
|---|---|---|
| `iPhone 15` | 264 | — |
| `iPhone 15 128G` | 59 | 29（占 49%） |
| `索尼 a7c2` | 33 | 0 |

> 数字是 2026-09-05 收尾时的实测。做决策时台账更小（128G 是 35 件、交集 15 件、43%），
> 中间因为 T1 验证跑了两次真实手动采集而变厚——**比例和结论没变**，两个口径都不干净。

两个 iPhone 关键词既非子集也非无关：窄关键词的 59 件里有 30 件宽关键词根本没看到。
两头都不干净——宽的混着各种容量与配件，窄的样本薄且漏掉标题没写容量的同配置机器。

**决策：一个关键词一张图，不提供多选合并。** 合并只会把非 128G 的机器混进 128G 的
行情，让口径更脏而非更准。真正的解法（解析标题按配置归一）是另一个功能。页面显式标出
「本图口径 = 关键词 X 的搜索结果」，让口径的粗糙可见，而不是用合并把它藏起来。

### 一处好消息

价格分布**不会被用户的价格区间截断**。`pipeline.screen()` 对每个搜索结果都返回
Candidate（含被本地过滤掉的），`store.persist_cycle` 对每个候选都建 `MonitorHit` 行
——实测 `in_range` 分布 312/44。所以它是真实市场分布，不是「符合我预算的那部分」。

## 真实采集照出的缺陷 · `214590e`

单元测试全绿之后跑真实采集，`POST /api/monitors/1/run` 返回 `collected: 30`，
而运行日志那一行写的是 `item_count = 0`。

原因：`record_manual_run(monitor_id, *, collector)` 从来没有 `item_count` 参数，
`_sync_record_outcome` 拿到的是默认值 0。**表里一个谎报 0 的成功行，和一个真的什么都
没搜到的周期完全无法区分**——这张表存在的理由正好被抵消掉。

**单元测试为什么漏掉**：我自己写的 `test_a_successful_manual_run_is_logged` 只断言了
`ok` 与 `collector`，没断言 `item_count`。测试断言的字段决定了它守得住什么。

修复后重启再跑一次真实采集，第 4 行 `item_count = 30`，与响应一致。这条来由写进了
测试注释。

## 供应量趋势画四态，不是三态

设计和 PRD 都说三态。实现给了四种，因为「未采集」其实是两件不同的事：

| 状态 | 画法 |
|---|---|
| 有新增 | 实心柱 |
| 采集正常但无新增 | **空心存根**——完全不画柱子会和斜纹区分不开 |
| 采集失败（`runs_failed > 0`） | 密斜纹，`--danger` |
| 无采集记录（`ok=0 且 fail=0`） | 疏斜纹，`--border-strong` |

不拆的话，运行日志开始之前的整段历史会读成一次长时间故障——这正是
`iPhone 15` 的 09-04（264 件新增 + 无采集记录）暴露出来的问题。

四种是**图案**差异而非仅颜色，另配图例、把未采集与失败天数计入的 `aria-label`、
以及带 `runs_ok / runs_failed` 的表格。

## 反向验证

M1 建立的标准：撤掉修复，测试必须失败。M2 做了 10 项。

| 撤掉的东西 | 变红 |
|---|---|
| `_sync_record_outcome` 里的运行日志写入 | 7 条 |
| 两处收藏循环的日志写入 | 6 条 |
| `_sync_record_run` 的 `try/except` 隔离 | 2 条 |
| 价格分布的「每商品取最新快照」 | 1 条 |
| `"collected": ok_count > 0` 改成恒 `True` | 4 条 |
| 供应量趋势改按 `Item.first_seen_at` 分组 | 1 条 |
| 在 `price_drops` 里塞一条 per-row `select` | 查询数 8（3 件）vs 25（30 件） |
| `method="inclusive"` 改回默认 | `assert -460000 >= 100000` |
| 成功路径不传 `started_at` | 「stamped at completion, not at the start」 |
| 过滤从 `PriceSnapshot.status` 挪到 `Item.status` | `assert 2 == 1` |

**一个方法论教训**：用 `cp` 备份回滚做反向验证时，恢复出的文件 mtime 可能比 `.pyc` 旧，
Python 会复用旧字节码——「恢复后测试仍然红」看起来像修复无效，其实是缓存。
反向验证必须 `touch` 源文件并清 `__pycache__`，否则会误判自己的修复。

## 对抗性评审照出的三个缺陷

四条命令全绿、真实数据看过、每项都留了反向验证之后，我仍然让一个独立子代理专门去**找错
而不是确认没错**。它找到了三个，其中一个严重。

### 1. 分位数会算出**负价格** · `app/analytics.py`

`statistics.quantiles(prices, n=20)` 默认 `method="exclusive"`，它把样本当作从更大总体中
抽出的，**样本少于 19 个时会外推到观测范围之外**。索引映射（1/4/9/14/17）是对的，方法不对。

实测，不是推理：

| 价格（分） | p10 | p25 | p50 | p75 | p90 |
|---|---|---|---|---|---|
| `[100000, 900000]`（¥1000、¥9000） | **-460000** | **-100000** | 500000 | **1100000** | **1460000** |

两件商品 ¥1000 和 ¥9000，分位数表会印出 **`P10 ¥-4,600`**——`formatPrice(-460000)` 照样
把它印出来。这不是"貌似合理但算错的图"，是一张**不可能存在**的图：除 p50 外每个值都落在
产生它们的那两件商品的范围之外。

改成 `method="inclusive"`，它在观测到的次序统计量之间插值，永远出不了 `[min, max]`。
这也是对这份数据更诚实的说法——模块自己的文档写着「这些是我们的搜索看到的商品，
不是市场的一个抽样」。

**我的测试为什么看不见**：`test_the_quantiles_are_the_percentiles_they_claim_to_be`
用了 100 个样本，在阈值之上。而 `sample_size == 2` 正是 PRD 列为验收项的
`sample_size == 1` 的下一个状态。新测试遍历 2–19 每个样本量。

### 2. `?keyword=`（空值）产生三个报错横幅 · `AnalyticsPage.tsx`

```ts
const keyword = fromUrl ?? keywords[0];   // "" 不是 nullish
```

手改过或被截断的分享链接给出 `""`，通过了 `??` 兜底，发到一个 `min_length=1` 的端点被
422 拒绝——而这一点正好被我自己的 `test_a_keyword_is_required` 证明过。URL 是信任边界，
`??` 不够，要 `||`。

### 3. 零峰值时坐标轴标签浮在图中间 · `DailyBars.tsx`

规则建了但从未采集时 `peak = 0`，唯一的 `0` 标签被 `scale(0, 0, 0, ...)` 定位——
零宽定义域被居中，于是那个 `0` 落在 180px 图的 y≈81：空轴的半空中。

**这和 `bucketRects` 已经用 `peak === 0 ? 0 : ...` 防过的是同一个根因**，只是没有把这个
守卫用到刻度标签上。修法只在 `scale()` 调用里 `Math.max(peak, 1)`——`peak` 本身保持诚实，
否则 `aria-label` 里的「最多一天 0 件」会变成谎话。

### 评审顺带指出的两件事，我也改了

- **`CollectRun.started_at` 是个死参数**：从来没有调用方传它，所以每一行装的都是**完成
  时间**。一个 23:59:50 UTC 开始、跑 30 秒的周期会被记到第二天，「那天采没采」就错了一天。
  实际窗口只有毫秒级，但**一个名字和内容不符的列会误导之后每一个读者**。已把真实开始时间
  从三条路径贯穿进去，并留了守卫测试（撤掉修复即变红）。
- **一条测不出东西的测试**：`seed_item` 把同一个 status 同时写进 `Item` 和每条
  `PriceSnapshot`，所以「已下架商品不算报价」这条测试**无论代码读哪一列都会通过**。
  已改成让两列故意不一致（`Item` 说在售、最后一次观测说已下架），现在把过滤挪到
  `Item.status` 就会变红。

### 评审证明为正确的几项（是证明，不是保证）

直方图分桶无 off-by-one，且那个 `min(..., count-1)` 夹取**可证明不可达**（已加注释说明，
免得有人在凌晨三点重新推导一遍）；`snapshot_ids_at(None)` 与重构前的
`newest_snapshot_ids()` 编译出的 SQL **字符串相等**，M1 调用点语义未变；查询数在
3 / 30 / **300** 件下分别恒为 3 / 5 / 4 条。

## 我自己踩的一个坑

`test_every_response_reports_how_much_data_is_behind_it[supply-trend]` 第一版失败，
`sample_size` 是 0。**代码是对的，测试错了**：种子把 `first_hit_at` 设成整整 30 天前，
而供应量趋势 `days=30` 的窗口起点是 `now - 29d`——刚好差一天落在窗口外。

这是三个端点 `days` 含义不同带来的认知负担——**同一个陷阱在收尾时又咬了我第二次**
（改测试时给了 `days=5`，supply-trend 的窗口起点是 `now-4d`，20 天前的首见又落在窗外）：

| 端点 | `days` 的含义 |
|---|---|
| price-distribution | 只算这段时间内被观测到过的商品 |
| price-drops | 拿这段时间起点的价比现价 |
| supply-trend | 图表横轴跨度 |

各自都是该指标的自然含义，但合在一起就会咬人。种子改成 20 天前，并把这段推理写在
常量注释里，下一个人读种子时不用重新踩。

## 一处需要提前说明、免得后人当 bug

四条降价记录的降幅**完全相同**（同窗口下都是 7.40% / 15.25%）。这不是算法错误：
`scripts/seed_demo.py:51` 的注释写明「Fractions of the real current price, oldest
first」——它按固定比例从真实现价反推更早的价格点。现价、标题、卖家是真的，价格序列的
历史点是合成的，同一批种子自然得到同一个降幅。

手算核对过：`(84960-72000)*10000//84960 = 1525` = 15.25% ✓

顺带验证了窗口语义：`days=1` 取到 09-02 的快照（7.40%），`days=3` 取到 08-31 的
快照（15.25%）——两个窗口确实取到了不同的「当时价」。

## 已定与未决

### 已定

- **不做多关键词合并**：会让口径更脏而非更准。
- **`status` 只用在一个方向**：确实观测到下架时排除该商品；不用它判定在售。
- **运行日志全量保留**，不降采样。外推 3 条规则 ≈ 47MB/年、10 条 ≈ 160MB/年，
  与快照的既有定案一致。降采样路径写在 `ponytail:` 注释里。
- **失败的手动运行不写运行日志**。它的失败已经以 502 告诉了触发者，且既有代码刻意不让
  手动探测计入 `consecutive_failures`。运行日志是解释**调度覆盖率**的，把手动探测的
  失败算进 `runs_failed`，那个数字就从「调度出过问题」变成「有人点过测试」。
  成功的手动运行照写——它确实观测了市场。

### 未决

- **降价排行现在是空的，要等历史攒够。** 最旧快照 `08-31 12:40`，7 天窗口起点
  `08-28 18:29`——没有「当时的价」可比，`days=7/30/90` 全为空。这是设计要的行为
  （窗口内新出现的商品不算降价），区块自己写明了原因，会随采集自己变有数据。
  **代码路径已在一份数据库副本上用真实行验证过**，不是没验就交。
- **`fresh_size` 对两个 iPhone 关键词是 0**，因为那两条规则是停用状态。
  「264 件，其中 0 件最近两轮仍在售」读起来别扭但准确。别当 bug 查。

### 按计划推迟

- **P3**：搜索翻页 + 消失时长指标
- **P4**：LLM 两个接入点 + 配置界面
- **P5**：卖家维度监控
